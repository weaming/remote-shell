# 远程脚本执行引擎设计

## 目标

实现一个轻量的远程脚本执行引擎，优先考虑 Go 或 Rust，运行环境覆盖 Unix/macOS 宿主机与容器。第一阶段聚焦局域网；执行端 Agent 尽量免配置、可靠稳定，客户端负责任务发起、输出查看和个性化处理。本文记录需求、方案分析和当前技术方向，不代表已经确定具体实现或依赖库。

## 原始需求

- 宿主机和容器都能运行或接入执行端；本机宿主与容器之间可通过本机通信互联。
- 节点之间可发现并通信，支持 P2P；减少中心控制面依赖。第一阶段仅做局域网，跨网能力以后再讨论。
- 优先 Go 或 Rust；通信开销小、协议通用。
- 支持可选鉴权，并防止不同机器间的网络中间人攻击。
- 远程执行完整命令字符串，shell 由执行器指定并解析。
- 支持 stdout、stderr 分别查看，也支持按输出观察顺序混合查看。
- 支持多任务并发；任务彼此独立。单个任务可以包含多条独立命令，可配置串行或并行，默认并行。
- 每条命令都必须指定工作目录，并可指定环境变量、stdin 和超时。
- 超时默认 5 分钟，最大 1 小时；支持取消，并返回退出码。
- 支持在任务结束前查看当前状态和已有输出（peek）。peek 与输出展示由客户端实现。
- 不设 Agent 侧输出量上限；脚本/客户端自行用 tail、grep 等方式控制输出。Agent 负责连接和执行，客户端负责缓存、处理和定制。
- 不缓存断线后的结果。默认断线即终止任务。
- 正常结束、非零退出、取消或超时后，清理命令及其受管后代：先终止，等待最多 10 秒，再强杀。
- 不增加外部进程监督；Agent 被强杀或后代脱离受管进程组后遗留进程，接受不处理。

## 方案分析

### 节点与发现

不设置必需的中心控制面。第一阶段在局域网用 mDNS 发现执行端；也可支持显式地址作为诊断或回退方式。跨网 NAT 穿透、协调节点和 relay 不纳入第一阶段。

宿主机与容器属于同机通信时，优先通过 Unix domain socket 接入宿主 Agent，并用 socket 文件权限及可用的本机进程凭据限制访问。不要仅凭 IP 地址或 loopback 判断是否同机。

### 通信与任务模型

QUIC 适合作为传输层：基于 UDP，提供可靠、有序的 stream 数据传输，并可在一个连接上复用多个双向 stream。建议每个任务使用独立 stream，同一客户端可并发提交多个任务；任务内串行/并行调度由 Agent 按请求参数执行。任务完成后关闭对应 stream；无活动任务时关闭连接。

stdout 与 stderr 分开采集和传输。每个输出块携带流类型和递增序号，客户端可按流查看，或按 Agent 观察到的序号合并。两个 OS 管道不能提供进程层面的全局真实写入顺序，因此混合顺序的定义是 Agent 采集观察顺序。

Agent 不持久缓存断线后的输出；输出实时流式发送。网络背压可能使读取管道变慢，实施时需要避免无界内存队列。客户端断开默认取消对应任务；需要在协议中定义任务状态和断线竞态的报告方式。

### 身份与鉴权

网络连接使用 QUIC 内置的 TLS 1.3 握手。TLS 负责加密与密钥协商，但必须另行验证身份才能抵御中间人攻击。

当前讨论方向是：Agent 用预置的公钥验证客户端身份，客户端以稳定唯一 ID 标识；Agent 尽量不要求用户手动配置。公钥可以编译进 Agent 二进制，私钥不能编入二进制。

身份机制仍需明确如何把客户端 ID 与公钥/签名绑定，以及客户端如何确认连接到预期的执行端身份。单纯传输一个 ID 字符串或使用未验证的自签证书不足以防 MITM。若需要双方身份认证，应在协议设计中分别定义客户端认证和执行端认证，不要把两者混为一谈。

### shell 与命令

仅支持 bash、fish、zsh；执行端只公布本机确实可用的 shell。请求必须明确指定 shell 和完整命令字符串，不根据启动 Agent 的默认 shell 猜测。不同 shell 语法不兼容，客户端需要按指定 shell 组织命令。

每条命令单独具有 cwd、环境变量、stdin、超时和命令 ID。默认并行执行；串行模式按请求顺序执行。命令之间在串行情况下可能通过文件等副作用相互影响，但每条命令的结果和退出码仍独立记录。任务级状态如何从多条命令结果汇总，需在协议阶段定义。

### 进程清理

Agent 为命令创建受管进程组/等效任务边界。取消、超时、断线取消及命令结束时，先请求终止受管进程组，等待最多 10 秒，再强杀仍存活成员并回收直接子进程及管道。

不承诺对主动脱离进程组、daemonize 或 Agent 被 SIGKILL 等情况作外部兜底；用户已明确接受不使用外部监督，可能遗留此类进程。Unix/macOS 的具体进程组实现与平台差异需分别验证。

## 当前技术实现方向

1. **语言**：Go 优先作为首选候选，因单二进制部署、并发和跨 Unix/macOS 支持较直接；Rust 仍是备选。最终应以原型验证和依赖成熟度决定。
2. **传输**：QUIC + TLS 1.3；每个任务一个双向 stream，同连接支持多个并发任务。
3. **发现**：局域网 mDNS；支持显式地址作为可选回退；无必需中心服务。
4. **本机接入**：宿主与容器之间优先使用 Unix socket，减少端口暴露和容器网络配置。
5. **任务协议**：任务请求包含 task ID、串行/并行模式（默认并行）和命令列表；命令包含 command ID、shell、命令字符串、必填 cwd、环境变量、stdin、必填 timeout。响应包含分块输出、命令状态/退出码、任务状态及取消/超时等结束原因。
6. **输出**：Agent 实时转发 stdout/stderr，不做断线缓存；块序号用于客户端混合展示与 peek 游标。客户端负责缓存和 UI/过滤逻辑。
7. **鉴权**：Agent 验证客户端公钥持有证明，并校验稳定客户端 ID；信任根/公钥的生成、写入、轮换与客户端验证执行端身份的方案仍待确定。
8. **调度**：任务独立执行；任务内默认并行，可选串行；Agent 设置可配置或有默认值的全局并发上限，避免资源耗尽。
9. **清理**：以 Agent 内部进程组管理实现 TERM → 最多等待 10 秒 → KILL；不依赖外部 supervisor。

## 尚待确定

- 语言与 QUIC 实现库，以及 mDNS 库的选择。
- 客户端 ID、公钥和私钥的生成/分发/存储方式；如何在免配置与可撤销之间取舍。
- 客户端如何验证执行端身份，避免只做单向客户端认证时仍遭遇假执行端/中间人。
- 任务级最终状态与多命令退出码汇总规则；串行遇到非零退出码后是否继续。
- 并行命令的输出顺序口径、取消传播以及任务并发上限。
- 无限输出与网络背压的具体行为，尤其是客户端消费速度低于命令输出速度时如何避免 Agent 内存无界增长。
- Agent 正常退出、崩溃和被强杀时分别能够保证的进程清理范围。
- mDNS 服务记录、Agent 能力查询和协议版本协商格式。
